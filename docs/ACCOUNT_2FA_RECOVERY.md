# 2FA 复活：账号令牌失效后自动重新登录

入口：管理员侧栏 → **2FA 复活**，地址 `/admin/token-guard-v2`。

这里的“复活”是用邮箱、密码和账号的 2FA 长期密钥重新登录，取得新令牌并恢复该账号的调度。不能解除封号、恢复已过期订阅、增加模型权限或保证 Astra 回答质量。站点管理员自己的两步验证不受影响。

## 怎样使用

1. 更新前后端并重启。主程序沿用原有迁移机制，执行新增的 `246_openai_oauth_recovery.sql`。升级前备份数据库。
2. 在“2FA 复活”页面确认凭据加密就绪。未配置时点击“一键启用”；服务器生成持久密钥，立即生效，不需要手填环境变量。
3. 点击“添加巡检账号”，选择已经导入的直接 OpenAI OAuth（登录授权）账号，填写登录邮箱、密码、2FA 密钥。2FA 密钥用于生成动态验证码，**不是当前的六位验证码**；没有开启账号 2FA 时可以留空。
4. 选择“使用账号代理”或已有的指定代理。没有代理时使用服务器直连；指定代理不可用时不会改成直连。
5. 保存后默认为这个明确选择的账号开启自动巡检和自动重登，可在列表分别关闭。新安装没有巡检账号，不会自动扫描其他账号。编辑已有资料时留空密码/2FA 保留原值，只有明确勾选清除才删除原 2FA。
6. 首次保存后，后台最多约一分钟开始准备本地登录进程，也可点击手动重登触发准备。查看“自动重登服务”状态：准备中时等待，运行中后可手动检查/重登。页面展示最近巡检、任务阶段和失败原因。

Linux amd64 / arm64 上，主程序自动下载并管理登录运行包，约 80 MB；服务器首次需要访问 GitHub，数据目录必须可写。运行包自带 Python、Node 和登录协议依赖，不需要安装独立浏览器、增加容器或配置内部令牌。无需 Prism 集成镜像，普通 Linux 网关也可使用。Windows 上显示平台不支持，不尝试执行 Linux 程序。

只接受普通登录授权账号；影子账号、API Key（接口密钥）、代理身份和个人访问令牌不适用。本次页面提供本机账密/2FA 登录，不配置第三方重登地址；后台拒绝 Session Studio 引擎。邮箱验证码链接和托管代理轮换没有作为本次页面功能开放。

## 自动恢复流程

默认每 30 分钟通过上游模型列表检查令牌。鉴权失败后每 5 分钟复检，连续失败 2 次且开启自动重登时进入持久任务队列，重登冷却时间默认 30 分钟；均可在规则页修改。网络、代理、限流等临时错误不按令牌失效处理。

默认同时处理 3 个登录任务，可在页面调整为 1–16。该上限按服务实例计算。任务采用数据库租约，同一账号的活跃任务不会重复入队；进程停止后，过期任务按原有超时策略处理。

写回前核对新令牌的账号、用户和邮箱，并比较登录前保存的凭据快照，拒绝错误身份或过时任务。成功时原子完成凭据写回、清除账号错误态、恢复调度和调度通知；保留模型映射及其他既有字段，同时失效令牌缓存。

关闭自动巡检或自动重登只控制后续自动操作；手动操作仍可使用。暂停或移除登记不会取消已经排队/正在执行的任务，也不会删除已经保存的登录秘密。更改登录凭据前注意当前任务状态；不要将重登成功当作封号或模型权限已经恢复。

## 凭据保存与备份

密码、2FA 及兼容字段在写入数据库前加密，后台查询仅返回“已配置”标记。管理接口不回显秘密，新增/修改资料的请求正文不进入审计日志。内部工作进程使用独立随机令牌认证，领取和提交均校验任务归属；数据库口令等无关环境变量不会传给登录进程。

有固定服务器加密密钥时复用既有加密器；否则单独保存到 `DATA_DIR/secrets/credential-operations.key`，默认 Docker 路径 `/app/data/secrets/credential-operations.key`。**数据库和这个密钥都要备份**。丢失密钥时不能解密原资料，程序不会用新密钥覆盖旧秘密。该密钥与站点用户 2FA、支付及 Prism 内部密钥分开。

### 原密钥不可用，选择放弃旧重登资料

更新后，原密钥缺失且数据库仍保存加密资料时，页面明确提示原因，并提供“清除旧重登资料并重新启用”。这个操作永久清除本功能保存的登录邮箱、加密密码、2FA 及兼容验证码链接；不会删除账号管理中的账号、原访问令牌、余额、站点两步验证或已结束的任务历史。之后需要重新添加巡检账号并填写登录资料。

执行前须移除全部巡检账号，且没有排队、运行中或写回中的重登任务。数据库事务锁定相关表并重新核对这些条件，然后只清理 `openai_oauth_reauth_configs`。已有可读密钥不会被替换；密钥损坏、权限错误或数据库读取错误也不会被当成“可以重置”。同实例的资料保存、任务创建与恢复操作互斥。

清理前先检查新密钥目录的持久挂载。若不满足条件，不删除旧资料；若清理已经完成但新密钥因权限等原因创建失败，页面会明确说明，修正权限后可重新检查并点击“一键启用”。该操作不是自动后台清理，接口要求管理员明确确认丢弃旧资料。

### 为什么数据库还有记录，而密钥不见了

数据库数据与密钥文件分别存储。将文件写进 `/app/data`，并不代表该目录已经挂到宿主机或数据卷。单纯重启同一个容器、重启服务器，通常会保留文件；更新时删除并重新创建容器，则会丢失容器自身文件层中的数据。即使存在挂载，换成空目录、新数据卷或更改 `DATA_DIR`，也会使新实例找不到原文件。若之前复用了固定服务器密钥，更新时没有保留原环境变量或配置文件也会造成类似问题。

本次现场确认的是“当前无专用密钥文件，固定密钥环境变量未设置”，没有取得旧容器挂载与配置，因此不能断言原文件一定被重启删除。

新初始化及上述恢复操作会检查 Linux Docker/Podman 容器的实际挂载信息：密钥所在目录必须位于独立、可写、非内存文件系统的挂载下；容器根文件层、只读卷和临时内存卷会被拒绝。不读取或挂载 Docker 管理接口。默认 Compose 文件已有 `/app/data` 挂载；其他容器面板部署须沿用固定的宿主机目录或数据卷。已配置的服务器固定密钥继续由部署环境保存，不自动替换。这项检查不能代替数据库、密钥和宿主机存储的备份。

恢复功能验证记录：提交 `5e09e47c2` 的自动测试 `37330685782` 已通过 Linux 密钥生成、文件权限、重启读取及恢复保护测试，并在隔离的 PostgreSQL 18 数据库实际验证清理事务：有巡检账号或活跃任务时拒绝清理；移除后只删除旧登录配置，原账号、访问令牌和已结束任务保留。另通过服务竞态检查、23 项前端测试、类型与规范检查及生产构建。没有操作用户服务器数据库；实际清理由管理员更新后在页面执行。

回退前关闭本页面自动开关并处理活跃任务，再回退主程序；保留数据库和数据目录，不删除密钥。新增表和设置不会被旧程序使用。正常主程序退出会停止托管登录进程。
