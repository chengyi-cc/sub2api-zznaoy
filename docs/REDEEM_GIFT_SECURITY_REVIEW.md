# 余额赠送兑换码安全复查（2026-10-26）

## 结论与范围

本次是赠送码生成、兑换、管理状态更新及开票的定向代码复查与本地测试，
不是整站渗透测试或“无漏洞”保证。改动尚未部署到生产环境。

## 本轮发现并修复的边界

原有批量更新会先读取兑换码，再检查是否已兑换，最后更新状态。
管理员操作与用户兑换交错时，兑换可以在前两步之后提交，随后管理员更新
把状态覆盖回未使用。单个作废接口也会把之前读取的整条记录重新保存，
有覆盖刚写入的兑换信息的风险。这些路径需要经过管理员权限检查，
不是匿名用户能直接修改状态的接口。

处理如下：

- 批量更新的实际数据库写入同时检查状态、兑换时间和兑换人；任一码不符合条件则整批回滚。
- 作废接口只更新状态，不再用过期的整条记录覆盖数据库。
- 兑换同时检查未使用状态和空的兑换记录，避免状态被错误重置后再次入账。
- 新增 `248_redeem_gift_consumption_guard.sql`（数据库升级脚本）：数据库触发器
  （数据库自动执行的检查）阻止已经消费的配对码被重新激活或清除兑换时间。
- 没有改写已提供的 247 升级脚本，便于已经应用过 247 的环境继续升级。

## 已验证的攻击与故障场景

- 使用真实路由注册和权限验证：匿名、无效登录凭证、普通用户、管理员声明与数据库角色不符、
  已禁用管理员、已撤销管理员凭证，均不能进入生成、编辑、作废、导出或读取兑换码接口。
- 用户兑换请求中注入金额、另一用户编号、赠送标记和配对编号，不能覆盖服务器保存的权益。
- 20 个并发兑换请求只成功入账一次；余额写入后发生错误时，兑换状态和余额一起回滚。
- 精确暂停管理员批量更新，让用户先兑换成功，再恢复更新：管理操作被拒绝、整批回滚、
  原码不能重复入账。该测试使用普通余额码，独立验证应用层保护，不仅依靠赠送码触发器。
- 修改赠送身份、配对信息、配对码金额、已经兑换的配对码状态或兑换时间，被数据库拒绝。
- 赠送码不能出现在可开票列表；直接伪造开票申请、混合提交正价码与赠送码，或引用赠送码
  进入最终开票步骤，均被拒绝。正价码仍能完成开票。
- 赠送余额不增加累计实付充值，不触发邀请返佣。
- 并发生成重试与响应缓存故障恢复返回同批已有兑换码；缓存只保存编号，不保存兑换秘密。
- 最大批次 500 组（1000 个码）与 0.01 正价对应 0.0001 赠送的精度边界通过测试。

本轮六个相关后端包的定向回归通过：业务服务、数据访问、路由、权限验证、管理员入口和
响应数据映射。临时 PostgreSQL（关系数据库）仅监听本机地址，测试创建独立数据库，
结束时删除测试数据库。前一轮前端测试和构建记录仍适用，本轮没有改动前端。

## 部署条件与未覆盖范围

- 必须应用 247 和 248 两个升级脚本，并升级所有后端实例后再发放赠送码。
  旧版后端不识别赠送标记，不能与新版混合承接此功能；回滚前应停用赠送码相关操作。
- 历史兑换码没有可靠的赠送属性，升级不会根据金额或备注自动推断、回填。
- 本次没有验证生产环境的反向代理、网络访问控制、管理员登录配置或数据库权限，
  也未执行全站依赖漏洞扫描或外部渗透测试。
- 管理员账户/管理密钥被盗、数据库管理权限被取得，仍是余额系统的高风险边界。
  兑换码本身是持有即可兑换的凭证，应限制查看、导出与传播范围。
- 前一轮扩大回归时，既有备份与凭据模块的 6 个测试因 Windows 缺少 sh
  （命令解释器）或目录同步拒绝访问而失败；这些既有环境问题不等于整套测试已通过。
