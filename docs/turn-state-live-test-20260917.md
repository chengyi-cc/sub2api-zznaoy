# 2026-09-17 真实账号与并发测试记录

测试地点：本地 Windows；出口为已部署的独立 IPv6（网络地址协议第六版）池。时间为 UTC+8（本地时区）。

## 结论

- 测试账号能完成一次 gpt-5.5（本次实际调用的模型）回答，未观察到 401（认证失败）。没有刷新账号凭据，也没有修改账号导出文件。
- 6 次该模型请求均返回 HTTP 200（请求进入响应处理），状态头均为 332 字符。其中 2 次流式探测报服务器过载，1 次完整结束并输出 2 个字符；另外 3 次是生产采集函数发出的短探测，只检查响应头后关闭流，不声称这些流最终生成成功。
- 正式采集的 3 次均被现行“只接受 292 字符”规则拒绝。没有擅自接受 332，也没有把成功回答推断成模型能力已恢复。
- 因没有合格状态，**没有执行“合格状态注入后 10 并发随机消息”**。不能把出口领取测试当成该项通过。
- 两轮真实 10 并发出口领取全部成功，20 个租约（临时出口使用凭据）和 20 个 IPv6 地址均唯一，释放后不再复用。
- 发现并修复大量账号首次采集时的等待问题：原实现槽位满后，需要后续请求或最长 30 秒周期检查才继续；现在任务结束立即调度待处理目标。

| --- | ---: | --- |
| gpt-5.5 首次账号探测 | 1 | HTTP 200；流式错误 server_is_overloaded（服务器过载）；状态长度 332 |
| gpt-5.6（账号映射中另一个模型名）探测 | 3 | HTTP 400（请求被拒绝）；无状态头；当次脱敏日志未确认具体原因，不据此判断账号无效 |

| 生产 acquire（状态采集函数） | 3 | 三个独立新出口；均因状态长度 332 被拒绝 |
| 合格状态注入后随机消息十并发 | 0 | 前置条件未满足，未启动 |

总计 9 次真实上游请求；本轮没有出现 401。不能只凭 HTTP 200 判断成功，测试还检查流内错误和完整结束事件。

## 多账号调度与容量

本地模拟 48 个账号，每账号 2 个模型，共 96 个独立采集目标。模拟只使用内存 Redis（用于隔离状态缓存的测试服务）与假上游，不消耗 48 个真实账号。

修复前：首批任务结束后其余目标不立即继续，5 秒内无法完成，回归测试失败。

修复后：96 个目标全部完成，每目标仅采集一次；单实例最大采集并发保持 4；首轮带数据竞争检测的该用例约 0.31 秒。增加失败冷却与关闭时不启动后续任务的回归检查；整个状态模块连续三轮数据竞争检测通过。

当前容量不是“任意账号数同时无限请求”：

- 单个 sub2api（业务转发服务）实例默认同时采集 4 个账号模型，剩余待处理；可配置 1–16。
- 新池预生成 24 个地址，每批最多生成 6 个，最多 32 个活跃租约、64 条代理连接；每租约最多同时 2 条连接。
- 多实例会共享池容量，应按所有实例的采集并发总和规划；共享缓存的分布式锁只避免同一账号模型重复采集，不是全局并发限额。
- 出口池库存耗尽可能返回 503（暂时不可用），租约上限可能返回 429（容量限制）；上游账号本身也可能限速或过载。
- 业务消息并发与采集并发不同。缓存命中后的业务消息不重新领取采集出口；本次账号配置的业务并发上限是 10，不代表上游保证接受十并发。
- 开关启用但没有合格缓存时，依照原设计继续原业务流程，不会保证每条请求都带新采集状态。

## 验证范围和复测方式

新增 live_test.go（必须显式启用的真实网络测试文件）。默认普通测试跳过真实网络调用，凭据仅从外部文件和进程环境读取，不提交账号、池密钥、完整状态值或代理密码。

真实账号测试通过 TURN_STATE_LIVE_TEST=1 开启，并设置 TURN_STATE_LIVE_ACCOUNT_FILE（单账号导出文件路径）、TURN_STATE_LIVE_MODEL（测试模型，默认 gpt-5.5）以及现有池环境变量。Windows 本地的 TURN_STATE_POOL_CA_FILE（可信证书路径）须指向本地 ca.crt 文件。运行命令：

    go test ./internal/turnstate -run=^TestLiveAccountTurnState$ -count=1 -v -timeout=8m

仅真实出口领取测试通过 TURN_STATE_LIVE_POOL_TEST=1 开启：

    go test ./internal/turnstate -run=^TestLivePoolConcurrentLeases$ -count=1 -v -timeout=2m

后续取得合格状态后，账号测试会将它写入隔离的内存缓存，再用生产 Apply（最终覆盖请求头的函数）为十条不同随机消息注入该值，检查注入一致性、完整结束事件与回复匹配。十条消息在十个临时业务出口上同时发出，以避免单租约两连接限制；这只是测试拓扑，不意味着实际业务每条消息都要新领出口。

该工具不是完整业务服务器的端到端测试：它验证真实采集函数和状态覆盖模块，不启动管理界面、生产数据库或完整网关。原 IPv6 服务和线上 sub2api 实例均未替换或重启。
