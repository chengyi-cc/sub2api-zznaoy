## 适配原则

- 比较同类能力，不将本机单用户默认值直接搬进多租户服务器。
- 保留当前 920000 token 自动压缩阈值、图片张数限制撤销、工具严格校验及账号/客户/线程隔离。
- 已发送模型请求后不因不确定的网络错误擅自重放；重试必须能证明边界、限制次数并合并用量。
- 参考代码存在某项能力不等于上游真实账号已支持，也不等于可证明降低端到端延迟。
- 保留本地未提交的安全并行提示修改，不在参考审计中覆盖、推送或部署。

## 本轮结论与优先顺序

四个项目使用同类 Excel/BPS 上游，但不是可互换的实现：本机桥接、CPA 插件与多租户服务器的并发、凭据、缓存和错误恢复边界不同。没有证据支持通过整体搬入某一个项目就让正常工具往返稳定缩短到某个秒数。

当前最值得优先做的是解压超限的明确处理、异常流的超时、下游断连检测，以及更准确的等待阶段记录。本轮只登记与审计，未导入这些运行时改动。原有 920000 token（模型文本计量单位）压缩策略保留。

## 本地发现的三个真实缺口

### 1. 解压后的 64 MiB 隐藏上限与静默截断

本地位置：backend/internal/pkg/httputil/body.go 的 maxDecompressedBodySize 和 decompressRequestBody（压缩请求解码函数）。HTTP 入口可配置且默认 256 MiB，但 gzip、deflate、zstd 的解压输出均另受 64 MiB 固定限制。读取器只取上限字节，没有多读一个字节判断超限，因而不返回明确的超限错误。

离线生成一个合法、解压后 67108876 字节的 JSON 请求，gzip 后只有 131597 字节。当前代码返回了 67108864 字节，错误为空，截掉 12 字节后结果不再是合法 JSON。这证明请求可能在完整上传后被本地截成格式错误，单独调大入口上限不能解决。

建议把解压上限与入口/路由策略明确区分并统一配置来源，有界读取到上限加一字节后返回 413（正文超过限制），同时保留解码内存和并发保护。不应直接为了“不报错”把多租户服务改为桌面项目的 1 GiB。

这是更大或多图片历史的兼容问题，不解释此前不到 1 MiB 的工具往返测试为何需要几十秒。

### 2. BPS 分支未使用配置的流空闲超时

本地位置：backend/internal/service/openai_excel_bps.go 的 scanner.Next(ctx, 0, heartbeat.C, keepalive)。第二个参数为 0，所以读取器中的空闲截止逻辑未启用。普通通道会读取 gateway.stream_data_interval_timeout（流数据间隔上限），其源码默认是 180 秒。

离线模拟把该字段缩短为 1 秒，以免测试等待 3 分钟。上游发出开始事件后完全静默，BPS 在 1.25 秒后仍保持读取，直到测试主动取消。读取器对照测试设 40 毫秒，则正常返回空闲超时。这证明的是 BPS 没有使用这一层的配置，不能据此声称实际请求永远没有任何外层截止。

实现时应观察原始上游是否还有数据。BPS 转换器会暂存工具参数，转换后的下游流暂时没有内容并不代表上游停止工作。直接把 0 改成 180 秒而不处理这一差别，可能增加大工具调用的误报。超时后应明确结束并保留已知用量，不把超时当作“请求未发送”进行重放。

### 3. BPS 未检测刷新时才出现的下游错误

本地位置：同文件 keepalive 和事件边界处直接调用 c.Writer.Flush()（把缓冲数据推向客户端）。普通通道的已有测试支持底层 FlushError。

模拟底层在刷新时返回 io.ErrClosedPipe（连接已关闭），普通通道对照测试正确识别；BPS 未调用可报告错误的接口，仍返回成功且 ClientDisconnect（客户端断连标志）为 false。验证的是调用链缺口，不是现实故障率统计。

应复用普通通道已经存在的错误识别和用量处理方式，避免继续向断开的客户端发送，且不能因此自动换账号重复生成。上述两项主要减少异常空等和错误成功统计，不能保证正常模型计算会更快。

## 各参考项目的新变化与不宜直接照搬的部分

### Kaixxrua/excel-codex-bridge v0.5.11

源码确认新增解压后 1 GiB 请求上限、分块解压、默认最多 120 秒连接恢复；此前已有默认 300 秒限流等待。连接恢复错误集合包含读取、写入、代理和协议错误，并不都能证明服务端没有收到模型请求。对多租户网关不宜整体复制这套重发规则；如果适配，只考虑明确发生在发送前的失败、很小的预算和完整的取消/用量边界。

我们的通用入口已有可配置 256 MiB 默认上限，但解压内部仍固定 64 MiB；应先修复两层边界和明确错误，而不是为对齐桌面项目直接改到 1 GiB。额度、压缩阈值和字节上限是不同概念。

桌面启动器可临时设置 features.apps=false、features.remote_plugin=false（关闭连接器和远程插件推荐），停止后恢复配置；提供保留开关。作者报告在其环境中减少了客户端额外联网等待，但本轮只核对源码与配置恢复测试，没有在用户当前桌面测量这个收益。当前用户配置未显式填写这两个值，不等于已确认它们的实际生效状态。未修改用户的 Codex 配置，也未关闭任何插件或连接器。

### JaxsonWang/cpa-plugin-oai-basispoints v0.2.6

新的工具中继以 references（外层工具名选择字段）路由，code（载荷字段）直接携带函数参数 JSON（结构化文本）或原文，减少工具名与参数的内层封装。我们已有部分原文传输能力，因此不是从零补齐；若尝试该形式，应新增明确版本契约并兼容旧调用，不能把现有 references 的用途悄悄改掉。

WebSocket（双向连接）仅在对应凭据 websockets 开启且传输策略允许时尝试，每轮握手，默认上限 5 秒；401/403/407/429 等认证或限流错误不换通道重试，连接选定并发送后也不再回退 HTTP 重放。源码每轮重新创建连接，没有可直接解决我们多轮历史上传的连接复用方案。单元测试使用模拟上游，不能证明真实账号支持。

该项目的原生工具回放缓存仍是进程全局、仅按调用编号索引，容量 512。不能用它替换我们按账号/客户/线程隔离的缓存。其结构化输出仍有明确不支持边界；我们已有本地验证能力，也不应因此退化。

### kokojacket/openai-proxy

比较的是 f1b6764 分支提交，而非仅旧 v0.1.0 发布包。大事件限额和隐私友好的事件体积日志值得参考；默认 8 个活动请求、32 个排队请求、120 秒排队和每秒 5 次上游启动，是单机代理的保护参数，不是官方账号配额。我们已有分组调度、并发与每分钟请求数控制，不叠加一套全局排队来增加等待。

离线调用实际请求构造函数确认：gpt-6-sol 被其别名表映射为 gpt-5.6-sol；未显式传策略时，其自动压缩阈值为 200000。不能拿这种同名请求的速度作同模型比较，也不会把我们保留的 920000 改回 200000。

其无工具纠正最多追加一轮、Office 封装纠正最多三轮、图片还有独立重试预算。它们是故障恢复策略，不是减少正常模型往返的优化。尤其“模型声称没有执行工具”后的自动补请求可能改变行为，不建议默认引入。

### ranxi2001/sub2api v2.9.2

新引入的 OAuth WS-to-SSE（上游双向连接、下游逐事件传输）模式明确排除 Excel/BPS，不代表它已经给 Excel 加了连接池加速。新增激活默认模式、自动配置历史、质量规则、凭据管理属于运维能力，是否引入取决于管理需求。

图片数量预警/自动压缩、容量放宽和成功流计数等修复有各自适用前提。我们已按用户要求撤销图片张数限制，不为了复用他们的图片限额策略而重新引入限制或额外压缩轮次。
